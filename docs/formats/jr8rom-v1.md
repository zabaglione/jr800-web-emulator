# JR8ROMアドレス付きROMコンテナー1.0

## 用途とデータの扱い

JR8ROMは、利用者が用意したJR-800 ROMのバイト列と、16ビットCPU上の論理アドレスを一緒に保存する形式です。
物理ROMの構成を推測せず、取得時に指定した範囲の境界を保ちます。

標準拡張子は`.j8r`、形式名とマジック識別子は`JR8ROM`です。
ROMデータ、ROMから作ったコンテナー、ROM由来の逆アセンブル、ROMを含むWAVはリポジトリへ追加しないでください。

`.rom`は`$8000-$FFFF`の32 KiBを並べただけのRAW形式です。
以前から使われている入力形式としてWeb UIで読み込めますが、アドレスと完全性検査を持たないため、保存と再利用には`.j8r`を推奨します。

## 意味モデル

コンテナーはSHA-256完全性値と、1個以上の格納セグメントを持ちます。
各セグメントは次の条件を満たします。

- 16ビットの論理開始アドレスを持つ
- データ列は空でない
- 終端は`$10000`を越えない
- 開始アドレスの昇順で、互いに重複しない

隣接セグメントは結合しません。
境界そのものが取得単位を表す場合があるためです。
アドレス間の空きは許可しますが、読み書き時に補完しません。

JR8ROMは、実行開始アドレス、ゼロ初期化セグメント、CPUプロファイル、物理ROM識別子、圧縮方式、入力パス、所有者情報を持ちません。

## バイナリー表現

整数は符号なしビッグエンディアンです。
バージョン1.0の固定ヘッダーは次のとおりです。

| オフセット | サイズ | フィールド | 条件 |
| ---: | ---: | --- | --- |
| 0 | 8 | magic | `JR8ROM`の後ろにゼロ2バイト |
| 8 | 2 | major version | `1` |
| 10 | 2 | minor version | `0` |
| 12 | 4 | flags | ゼロ |
| 16 | 32 | integrity SHA-256 | 後述のダイジェスト |
| 48 | 4 | segment count | 1～65,535 |

ヘッダーの後ろに`segment count`個のレコードを置き、各レコードの直後へデータを格納します。

| 相対オフセット | サイズ | フィールド | 条件 |
| ---: | ---: | --- | --- |
| 0 | 2 | logical address | 直前の開始アドレスより大きい |
| 2 | 4 | data length | 1～65,536。16ビット空間内に収まること |
| 6 | data length | data | 指定長の格納データ |

パディングと末尾の余分なデータは許可しません。
開始アドレス0、長さ65,536の1セグメントで64 KiB全体も表現できます。

## 正規順序と完全性

ライターはセグメントを論理アドレス順に並べます。
読み込み時にこの順序でないファイルは、同値表現として並べ直さず無効とします。

SHA-256の入力は次のバイト列です。

1. ASCIIの`JR8ROM-INTEGRITY-V1`
2. ゼロ1バイト
3. ビッグエンディアン`u32`のセグメント数
4. 各セグメントの開始アドレス`u16`、データ長`u32`、データ本体

ダイジェストはアドレス、長さ、境界、順序、内容をまとめて検査します。
マジック、バージョン、フラグ、個数、順序、範囲、入力末尾、ダイジェストの全条件を満たした場合だけ受理します。

## 読み込み側の条件

正しいJR8ROMでも、必要なアドレス範囲の一部しか持たない場合があります。
利用側は必要範囲を明示し、1バイトでも欠けていれば拒否します。
空きを推測値で埋めたり、隣接レコードを結合したり、再配置したり、物理ROM名を推測したりしません。

JR-800エミュレーターは`$8000-$FFFF`の32 KiB全体を要求します。
Native版の`jr8run jr800`は、完全に検証したJR8ROMからこの範囲を取り出します。
Web UIは同じC++処理で`.j8r`を検証します。
`.rom`を選んだ場合だけ、確認後に32 KiBの固定範囲として直接読み込みます。

作成、結合、検証、抽出には[`jr8rom`](../sdk/jr8rom.md)を使います。
WAVからの変換には`jr8wav`を使います。

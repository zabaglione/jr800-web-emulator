# 11 1ドットと8ドットのスクロール

テンキー4を押している間は左へ、6なら右へ移動します。5を押すたびに1ドット／8ドットを切り替えます。画面中央の数字が移動量です。

## 使用する部品

新しいライブラリは **scroll.s + keys.s** のみです。ほかに共通のLCD表示・文字・BASIC復帰処理をリンクします。ライブラリの契約は[API解説](../../../lib/README.md)にあります。

## 実行

このフォルダーで次を実行します。SDKとWASMの準備、通常のWeb画面でのファイル読み込みは[共通ガイド](../README.md)を参照してください。

```sh
make
make run
make debug
make test
make clean
```

生成される実行ファイルはリポジトリの`build/sdk-lcd/11-scroll-steps/11-scroll-steps.j8a`です。BREAKでのBASIC復帰は既存のJR-HuBASIC 1.0用処理を使用します。09〜13の復帰を所有ROMや実機で新たに検証したものではありません。

## ソースを読む順序

1. `pattern`で横192×縦8ドットの模様を作ります。
2. `move`で押下中のビットを見て方向を決めます。
3. Xに帯の先頭、Aに移動量を渡して`scroll_left/right`を呼びます。
4. 5の切替には押下イベントを使い、押しっぱなしで何度も切り替わるのを防ぎます。

空いた端は0になります。循環スクロールや新しい模様の補充は行いません。1ドットと8ドットで処理時間が大きく変わらない理由は、どちらも帯のほぼ全バイトを移動するためです。

## 変更して試す

`amount`を6に固定し、共通フォント1文字分の移動に変更します。発展課題は、空いた端へ新しい模様を書いて流れを途切れさせないことです。

## RAMと検証

実際の使用量はPROGRAM 1,082／STATE 10バイトです。PROGRAMにはコードと文字・画像などの固定データ、STATEにはライブラリを含む状態を数えています。共通して画面バッファー1,536バイト、復帰処理76バイト、退避・コピー用132バイト、CPU内作業領域18バイト、スタックが別に必要です。アドレス配置の予約範囲は使用量より大きいため、空き容量は`.map`を見て判断します。

左右の移動結果、空いた端の消去、1/8切替、5を押しっぱなしにした場合を確認しました。 全画素のLCD転送とスタックも検査します。結果は`verification.json`、最初の画面は`screen.svg`です。実機とカセット転送は未検証です。

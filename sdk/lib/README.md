# 省RAMの機械語ライブラリ

JR-800用の独立したMITライセンスのHD6301V1ソースです。必要な`.s`だけアセンブルしてリンクします。ROMの音処理や字形は使いません。使用例は[08 共通ライブラリ実験室](../examples/lcd/08-library-lab/README.md)です。

## 実現範囲

| 項目 | 今回の実装と現実的な使い方 |
| --- | --- |
| SE | 単音、音程の切り替え、休符を表で指定。短い決定音・取得音向け |
| BGM | 単音の旋律は再生可能。ただし今回の再生はCPUを占有するので、ゲーム進行と並行する連続BGMには使えない。タイトル・クリア時の曲、ターン間の短いフレーズ向け |
| スプライト | 幅1〜192×高さ8ドットの部品を任意のドット位置へOR/XOR合成。右端・下端を切り詰める。複数の部品で大きい図形を構成する |
| スクロール | 横192×縦8ドットの帯を左右へ1〜191ドット移動。1ドット／8ドットを選択可能。空いた部分は0。地面など少数の帯に限定する |
| キー | 押下中・押した瞬間・離した瞬間。短い入力を複数回の走査にまたがって保持可能。汎用ビットマスクAPIとテンキー行の読み取りを分離 |

JR-800そのものでBGMが絶対不可能、という結論ではありません。既存の音の方式はCPUでPort 1 bit 4を反転する方式で、独立した音源が自動で鳴り続ける方式は確認できていません。描画と並行する安定した発音には、周期処理とLCD転送を含む実行時間の管理が必要です。既存サンプルはSEIで割込みを禁止しており、BASIC側の割込みを有効化するだけでは作業RAMや復帰処理との安全な共存を保証できません。この調査では連続BGM・和音・BGMとSEの同時再生を提供しません。

## RAMとリンク

**プログラムコードと固定データもJR-800のRAMを使います。** 以下の作業領域だけで収まるという意味ではありません。数値は付属jr8asの現在の出力です。

| モジュール | コード | 作業RAM | 呼出側のデータ |
| --- | ---: | ---: | --- |
| `keys.s` | 60バイト | 0 | 状態3バイト／入力グループ |
| `sprite.s` | 144バイト | 12バイト | 画像は幅と同じバイト数／8ドット高 |
| `scroll.s` | 128バイト | 6バイト | 追加バッファー不要 |
| `sound.s` | 117バイト | 7バイト | 音符4バイト、終端4バイト |

描画は呼出側が定義した`framebuffer`シンボルの1,536バイトを共有します。二重バッファー、画像キャッシュ、スプライト一覧、背景退避領域は確保しません。固定データはロードされた位置から直接参照します。`.bss`はリンクスクリプトで配置するため、CPU内RAMの固定アドレスをライブラリが占有することもありません。

すべてA/B/X/条件コードを破壊してよい呼出規約です。描画・音はモジュール内の作業領域を使うため再入不可です。同じモジュールを割込みとメイン処理から同時に呼ばないでください。キー処理はXの状態レコードを使用します。スタックには通常のJSRに加えキー保持処理の2バイトなどを使います。サンプルはスタック上端を`$5FFF`に設定します。

既存LCDサンプルへの組み込みは[08のMakefile](../examples/lcd/08-library-lab/Makefile)と同じです。不要なモジュールは`SOURCES`から外します。リンカーが関数単位で削除する前提にはしていません。01〜07のゲーム固有処理をこのライブラリへ置き換える変更は含みません。

## スプライト

呼ぶ前に`sprite_width`へ幅、`sprite_mode`へ0（OR）または1（XOR）を設定します。Xに画像先頭、Aにx、Bにyを渡して`JSR sprite8`を呼びます。1バイトが縦8ドットで、bit 0が上です。

```asm
    LDAA #8
    STAA sprite_width
    CLR sprite_mode
    LDX #image
    LDAA #24
    LDAB #19
    JSR sprite8
```

原点は符号なしでx=0〜191、y=0〜63です。負座標を表す折り返し値には対応しません。範囲外の原点、幅0または193以上、mode 2以上は何も描きません。画像全体の幅分の読み出し可能領域を呼出側が用意します。

16×16画像なら上半分16バイトを(x,y)、下半分16バイトを(x,y+8)に描きます。画面外になる下半分は呼出側で省略し、8ビット座標の加算オーバーフローを避けてください。透明部分は背景を保持します。ORは上書き消去できません。移動前の背景を描き直すか、背景が変化しない区間で同じXOR画像をもう一度描いて消します。スクロールの前にはXORスプライトを消し、スクロール後に描き直します。

## スクロール

Xに対象の192バイト帯の先頭、Aに移動量を指定して`scroll_left`または`scroll_right`を呼びます。

```asm
    LDX #framebuffer + 768
    LDAA #8
    JSR scroll_left
```

A=0または192以上は何もしません。Xの範囲は呼出側の責任です。縦スクロール、任意幅の矩形、循環スクロールではありません。複数帯を同じ量だけ移動させれば高さ16ドット以上の領域になります。8ドット移動は8×8文字なら1文字分ですが、共通の5×7フォントは文字間込み6ドットなので、1文字分は6を指定します。空いた端への新しい地形や文字の描画は呼出側が担当します。

## キー入力

Xは`held, pressed, released`の3バイトを指します。最初に`keys_reset`で初期化します。入力はactive-high（1が押下）です。

| API | 動作 |
| --- | --- |
| `keys_update` | Aの現在値から今回の押下／解放を計算。前回のイベントを置き換える |
| `keys_latch` | Aの現在値から押下／解放を追加。イベントを蓄積する |
| `keys_ack` | 押下／解放イベントを消す。押下中の状態は保持 |
| `keys_keypad` | `$0FFE`を読み、反転して`keys_latch`へ渡す |

`keys_keypad`のbit 4/5/6/7はテンキー4/5/6/7です。別のキー行やアプリの操作割当は呼出側でビットマスクに変換します。ハードウェアのマトリクスが区別できない同時押しを、この処理が復元できるわけではありません。

イベントを処理して`keys_ack`を呼び、LCD転送の各区間や待ちループの途中で`keys_keypad`を呼ぶと、1フレーム中の短い入力を保持できます。押下と解放が同じフレームに起きれば両方のビットが立ちます。回数・順序は保持しません。デバウンス、自動リピート、未走査区間の入力保証は含みません。08では待ちを約3.3msずつに区切り、LCDの32転送区間の間でも走査します。SE再生中は走査しません。

## SEとメロディー

`sound_tone`はXに遅延回数N（1〜65535）、Dに波形の周期数（0〜65535）を渡します。N=0または周期数0は何もしません。Port 1の出力値は読まず、`sound_port`に呼出側が与えた出力値のbit 4だけを切り替えます。終了時のbit 4は0です。

**Port 1の全出力値と方向設定は呼出側の管理対象です。** `$0002`の読み値を以前の出力ラッチとみなしてはいけません。ライブラリはDDRを変更せず、他のドライバーとの調停もしません。08の`$EF`という出力値とDDR `$10`は単独デモの明示的な設定で、BASICの元のラッチを復元した値ではありません。他の周辺機能との共用、実機での起動状態・復帰時の影響は未検証です。

割込みなしの実行で、連続したHigh期間は`4N+12`、Low期間は`4N+30` Eサイクルです。公称1,228,800Hzからの計算式は`周波数 = 1228800 / (8N+42)`です。たとえばN=344は約439.8Hzです。BASICのSOUND引数とは異なります。CPUの発音ループ全体をテストしており、単に待ちループだけを音程計算に使っていません。

`sound_play`はXで次のような表を参照します。

```asm
    LDX #effect
    JSR sound_play
; delay, periods。periods=0で終了。
effect:
    .word 340,32
    .word 170,32
    .word 0,2000  ; 約6.5msの休符（4*2000サイクル＋処理時間）
    .word 0,0
```

表の終端は必須です。長さ引数はなく、壊れた表を検出する機能はありません。遅延0のレコードは周期数を待ち回数として使う休符です。`sound_rest`単独はX回の待ちだけを行い、Portを変更しません。長い曲はBREAK走査も止めるため避けてください。SEと曲の同時再生や優先順位付きキューはありません。

## 実行時間と落とし所

NativeのHD6301V1命令実行による測定値です。時間は公称Eクロック換算で、実機のLCD BUSY時間の測定ではありません。サイクル値はテストドライバーの引数ロードとJSR/RTSを含みます。

| 処理 | Eサイクル | 換算時間 |
| --- | ---: | ---: |
| 8×8 OR、y=0 | 1,190 | 約0.97ms |
| 8×8 OR、y=7 | 2,086 | 約1.70ms |
| 1帯を左へ1ドット | 7,516 | 約6.12ms |
| 1帯を左へ8ドット | 7,306 | 約5.95ms |
| 1帯を右へ1ドット | 7,526 | 約6.12ms |
| 1帯を右へ8ドット | 7,351 | 約5.98ms |

移動量が8倍でも速さが8倍になるわけではありません。毎回ほぼ192バイトを書き換えるからです。全8帯のスクロールだけで約48〜49msかかり、さらにLCD転送が必要です。08のWASMで待ちと入力走査を含む通常更新は約127ms、1帯移動時は約133msです。これは最大性能ではなく、待ちを入れたサンプルの実測です。待ちを削っても、全画面60fpsをこの方式で達成することはできません。

まず1〜2帯のスクロールと少数の8×8スプライトを使い、地形の追加・古い絵の消去・LCD転送を含めて測る方針を推奨します。単独ライブラリーのサンプルは既存のBUSY対応転送を共有します。完成ゲーム向けには、末尾で説明する`lcd/dirty.s`の部分転送を追加しています。ハードウェアスクロールの仮定は追加していません。

## 検証

```sh
cmake --build --preset native-release --target sdk_library_test
ctest --preset native-release -R '^sdk_library_test$'
make -C sdk/examples/lcd/08-library-lab test
```

Native検査は全65,536通りのキー遷移、イベント保持、画面端を含む縦位置と幅・OR/XOR、左右512条件のスクロール、48条件の音の周期・ポート値、休符付き音列表を確認します。WASM検査はキー操作で描画・帯移動・SE・メロディー・押しっぱなし時の非再発音と全画素／スタックを確認します。成果物と実測は`build/sdk-lcd/08-library-lab/`へ出力します。

NativeのRAMバス検査は機械語の契約を、WASM検査は既存JR-800モデルへの組み込みを確認します。今回のブラウザーGUI操作、音の試聴、実機実行、カセット転送、電気的なタイミングは未検証です。

単独利用の例は[09 音](../examples/lcd/09-sound-sequence/README.md)、[10 スプライト](../examples/lcd/10-sprite-xor/README.md)、[11 スクロール＋キー](../examples/lcd/11-scroll-steps/README.md)、[12 キー](../examples/lcd/12-key-edges/README.md)です。組み合わせたゲームは[13 STAR COURIER](../examples/lcd/13-star-courier/README.md)にあります。

## 完成ゲーム用の共通部品

`lcd/`にはサンプルと完成ゲームが共有する表示・独自フォント・BASIC復帰を配置しています。`lcd/dirty.s`は同じ1,536バイトの描画面を使い、8帯それぞれの変更した横範囲だけを転送します。

- `dirty_reset`は範囲を空にし、`dirty_all`は全画面を変更扱いにします。
- `dirty_mark`はA=帯（0〜7）、B=横座標（0〜191）で、範囲の両端を登録します。
- `dirty_begin`の後、`dirty_next`をZ=1になるまで呼びます。1回は最大1個のLCD区間で、呼び出し間に入力を走査できます。転送数は`dirty_bytes`です。
- 部分更新では、背景を含む移動前・移動後の内容を呼出側で描き直してください。範囲登録だけでは残像を消せません。描画中と転送中のフレームバッファー変更を重ねないでください。

`game-input.s`はテンキー8/2/4/6とW/S/A/Dを、上・下・左・右の論理ビット1/2/4/8へまとめます。SPACE=16、RETURN=32です。同方向の別キーは合成してから押下判定し、反対方向は相殺します。`input_init`、反復する`input_poll`、消費時の`input_take`を使います。`input_gate`は全キー解放まで次の操作を抑えます。BREAKは共通のBASIC復帰を呼びます。

1ティックはCPU内蔵タイマーの20,000 Eサイクルです。方向のリピートは初回20ティック、以後6ティックです。16ビットカウンターの1周（65,536サイクル）より短い間隔で走査してください。ゲーム本体は描画・転送・短い旋律の間にも走査します。フレームバッファーの2重化やホスト側での入力変換には依存しません。

LCDのBUSY待ち自体が実機で長引く場合の入力間隔は実機検証が必要です。今回の短い旋律は発音を細かく区切って走査する方式で、同時BGMではありません。[ゲームの検証記録](../../docs/games/validation.md)を参照してください。
